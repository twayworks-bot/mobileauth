## 2. 파트별 상세 설계 및 개발 내역

### 파트 A. 개발자 등급 (`developer` Flag: `0` ~ `2`) 데이터 모델 및 인증 검증 설계

#### A-1. 등급 체계 정의
기존 관리자 등급(`manager` flag)과 독립적(직교, Orthogonal)으로 동작하는 **개발자 등급(`developer` flag)** 속성을 Keycloak User Attributes에 추가합니다. 한 사용자가 관리자 등급과 개발자 등급을 동시에 가질 수 있습니다 (예: `manager="1"`, `developer="2"`).

| 구분 | 속성명 (Keycloak Attribute) | 등급 값 (`Flag`) | 명칭 (Role Name) | 권한 및 용도 |
| :--- | :--- | :---: | :--- | :--- |
| **관리자 등급** (기존) | `manager` | `"0"` | 일반 `user` | 일반 서비스 이용, 본인 프로필/PIN 관리 |
| | | `"1"` | 일반 관리자 (`admin` / `manager`) | 각 서브 서비스(Booking, Bus 등)의 비즈니스 관리자 기능 |
| | | `"2"` | 최고 관리자 (`super`) | 중앙 사용자 관리 대시보드(`/auth/users`) 접근 및 전체 권한 부여/삭제 |
| **개발자 등급** (**신규**) | `developer` | `"0"` | 일반 `user` (비개발자) | 개발자 전용 기능 및 로컬 개발 예외 API 사용 불가 |
| | | `"1"` | 일반 개발자 (`developer`) | 서브 앱 개발자 권한, **로컬 개발용 예외 인증 API 호출 허용**, 개발용 메뉴 접근 |
| | | `"2"` | 개발 리더 (`dev-leader`) | 리드 개발자 권한 (`developer` 권한 포함 + 개발 리더 전용 기능/설정 접근) |

* **부트스트랩 계정 보호**: 최상위 계정(`01055787363`)은 항상 `manager="2"` (`super`) 및 `developer="2"` (`dev-leader`)를 반환하도록 보장하며, 권한 강등 및 삭제를 차단합니다.

#### A-2. 파일별 수정 내역 (`developer` Flag 반영)

1. **`configure_keycloak_schema.py` (Keycloak 스키마 자동 구성)**:
   * `holyseeds` Realm의 Declarative User Profile 설정에 `developer` 커스텀 속성을 자동 추가하도록 확장합니다.
   * 속성 정의:
     ```python
     {
         "name": "developer",
         "displayName": "Developer Flag (0=User, 1=Developer, 2=Dev-Leader)",
         "permissions": {"view": ["admin", "user"], "edit": ["admin", "user"]}
     }
     ```

2. **`keycloak_api.py` (서비스 레이어 함수 추가)**:
   * `get_user_developer_flag(user: dict) -> str`:
     * 사용자의 `attributes.developer` 값을 읽어 `"0"`, `"1"`, `"2"` 중 하나를 반환 (미설정 시 `"0"`, 부트스트랩 계정 `01055787363`은 `"2"` 반환).
   * `get_developer_role_name(dev_flag: str) -> str`:
     * `"0"` -> `"user"`, `"1"` -> `"developer"`, `"2"` -> `"dev-leader"` 반환.
   * `is_developer(user: dict) -> bool`:
     * `get_user_developer_flag(user) in ("1", "2")` 여부 판정 (일반 개발자 및 개발 리더 모두 `True`).
   * `is_dev_leader(user: dict) -> bool`:
     * `get_user_developer_flag(user) == "2"` 여부 판정 (`dev-leader`만 `True`).
   * `set_user_developer_role(user_id: str, dev_flag: str) -> dict`:
     * 사용자의 `attributes.developer`를 `["0"]`, `["1"]`, `["2"]`로 업데이트 (부트스트랩 계정 변경 방지 포함).
   * `signup_user(...)`:
     * 신규 가입 시 기본 속성으로 `"manager": ["0"]`, `"developer": ["0"]`을 명시적으로 초기화.

3. **`routes.py` (인증 절차, 세션 검증 및 권한 관리 라우터 확장)**:
   * **로그인 게이트웨이 (`GET /auth/login`, `POST /auth/login`)**:
     * `require_role` 파라미터 처리 강화: 로그인 시 `require_role`이 전달된 경우(`developer`, `dev-leader`, `manager`, `super` 등) 로그인 직후 해당 사용자가 요구 등급을 충족하는지 검증하고, 미충족 시 에러 메시지와 함께 로그인 화면에 안내하거나 콜백으로 권한 여부를 전달.
   * **세션 검증 API (`GET /auth/api/verify-session`)**:
     * 응답 JSON에 개발자 등급 관련 필드를 표준 포함하여 서브 앱이 즉시 활용할 수 있도록 확장:
       * `developer_flag`: `"0"` | `"1"` | `"2"`
       * `developer_role`: `"user"` | `"developer"` | `"dev-leader"`
       * `is_developer`: `bool` (`developer_flag in ("1", "2")`)
       * `is_dev_leader`: `bool` (`developer_flag == "2"`)
       * `roles` 배열 확장: `is_developer`이면 `"developer"` 추가, `is_dev_leader`이면 `"dev-leader"`, `"dev_leader"` 추가.
     * `require_role` 쿼리 파라미터에开发자 등급 검증 추가:
       * `require_role`이 `"developer"`, `"role:developer"`인 경우 -> `is_developer` 검증.
       * `require_role`이 `"dev-leader"`, `"dev_leader"`, `"role:dev-leader"`, `"role:dev_leader"`인 경우 -> `is_dev_leader` 검증.
       * 복합 조건이나 커스텀 속성 검증도 기존과 동일하게 하위 호환 유지.
   * **사용자 관리 대시보드 (`GET /auth/users`, `POST /auth/users/{user_id}/set-developer`)**:
     * `users_get`에서 각 사용자 객체에 `developer_flag`, `developer_role`, `is_developer_flag`, `is_dev_leader_flag`를 주입.
     * `POST /auth/users/{user_id}/set-developer` 라우트를 신설하여 최고 관리자(`Super`, `manager == "2"`)가 사용자의 개발자 등급(`0`: 일반 user, `1`: developer, `2`: dev-leader)을 드롭다운으로 즉시 변경할 수 있도록 지원.
   * **내 프로필 (`GET /auth/profile`, `POST /auth/profile`)**:
     * 템플릿 컨텍스트에 `developer_flag`, `developer_role`, `is_developer`, `is_dev_leader`를 전달.

4. **`templates/profile.html` & `templates/users.html` (UI 업데이트)**:
   * `profile.html`: 기존 관리자 등급 뱃지 옆에 개발자 등급 뱃지 표시 (`🛠 개발 리더 (dev-leader / 2)`, `💻 개발자 (developer / 1)`, 또는 미표시/일반 사용자). 또한 개발자(`is_developer == True`)인 경우 로컬 개발 연동용 **내 세션 ID / 로컬 개발 검증 토큰 확인** 안내 영역을 선택적으로 표시.
   * `users.html`: 사용자 목록 테이블에 **[개발자 등급 (0/1/2)]** 컬럼 및 드롭다운 변경 폼(`일반 user (0)`, `developer (1)`, `dev-leader (2)`) 추가.

### 파트 B. 로컬 개발 환경을 위한 외부 공개 인증앱 직접 호출(Direct Call) 예외 API 및 메커니즘 설계

#### B-1. 문제 원인 상세 분석
서브 애플리케이션(예: Booking, Bus 등)을 개발자의 로컬 PC(`http://localhost:5000` 또는 `http://127.0.0.1:3000`)에서 개발할 때, 외부에 배포된 중앙 공개 인증앱(`https://holyseeds.thewayworks.net/auth`)을 연동하면 다음 **2가지 근본적인 장벽**이 발생합니다:

1. **도메인 불일치로 인한 쿠키 미전달 (Cross-Origin Cookie Isolation)**:
   * 사용자가 `https://holyseeds.thewayworks.net/auth/login`에서 로그인하면 `auth_session` 쿠키는 `holyseeds.thewayworks.net` 도메인에 구속됩니다.
   * 이후 로컬 앱(`http://localhost:5000`)으로 돌아오거나 로컬 앱을 호출할 때, 브라우저는 `localhost`에 `holyseeds.thewayworks.net`의 쿠키를 전송하지 않으므로 로컬 앱 백엔드는 사용자의 `session_id`를 알 수 없습니다.
2. **외부에서 로컬 Callback 주소 접근 불가 및 리다이렉트 제약**:
   * 공개 인증 서버(클라우드/외부망)가 백채널(Server-to-Server)로 `http://localhost:5000/callback`을 호출하려고 하면 외부 서버 자신의 loopback을 가리키므로 연결이 불가능합니다.
   * 또한 브라우저 프론트채널 리다이렉트를 쓰더라도 세션 정보를 쿠키가 아닌 명시적인 파라미터(또는 로컬 직접 호출 API)로 넘겨받지 못하면 로컬 앱은 공개 인증앱에 검증 요청을 보낼 수 없습니다.

#### B-2. 해결 아키텍처: 로컬 개발용 예외 API 및 세션 전달 플로우 (2가지 방식 지원)

로컬 개발자가 앱 코드를 수정하지 않거나 최소한의 설정만으로 외부 공개 인증앱(`https://holyseeds.thewayworks.net/auth`)에 직접 Call하여 인증 Verification을 수행할 수 있도록 **2가지 예외 연동 메커니즘**을 함께 제공합니다.

```
[방식 1: 로컬 앱 -> 공개 인증앱 Direct Auth & Verify API (콜백 자체가 불필요한 직접 호출 방식)]
+-----------------------+   (1) POST /auth/api/dev/login-token    +-----------------------------------+
|  로컬 개발 앱 백엔드  | --------------------------------------> |     외부 공개 인증 프록시 서버    |
| (http://localhost:*)  |       (phone, pin 또는 기존 session)    | (holyseeds.thewayworks.net/auth)  |
|                       | <-------------------------------------- |  * developer 등급(>=1) 필수 검증! |
|                       |   (2) session_id + dev_verify_token 반환|                                   |
|                       |                                         |                                   |
|                       |   (3) GET/POST /auth/api/dev/verify     |                                   |
|                       | --------------------------------------> |  * 세션 & manager/developer 등급  |
|                       | <-------------------------------------- |    실시간 Verification 결과 반환  |
+-----------------------+       (Header/Query로 세션 직접 전달)   +-----------------------------------+

[방식 2: 공개 인증앱 웹 로그인 후 로컬 주소로 세션 토큰 직접 전달 (Localhost ब्र릿지 모드)]
(1) 브라우저가 https://holyseeds.thewayworks.net/auth/login?redirect=http://localhost:5000/auth/callback&dev_mode=1 접속
(2) 공개 인증앱에서 로그인 성공 시:
    - redirect 대상이 localhost / 127.0.0.1 이고,
    - 로그인한 사용자의 developer 등급이 1(developer) 또는 2(dev-leader) 인 경우에만 허용!
(3) 공개 인증앱이 http://localhost:5000/auth/callback?session_id=<UUID>&dev_token=<HMAC서명토큰> 으로 브라우저 리다이렉트
(4) 로컬 앱은 전달받은 session_id(또는 dev_token)를 로컬 쿠키에 저장한 뒤,
    공개 인증앱의 https://holyseeds.thewayworks.net/auth/api/dev/verify (또는 /auth/api/verify-session)에
    직접 Outbound Call을 보내 인증 및 권한(manager, developer 등) Verification 수행!
```

#### B-3. 신규 제작할 로컬 개발 예외 API 상세 명세

##### 1) `POST /auth/api/dev/direct-login` (로컬 개발용 Direct 세션 발급 API)
* **용도**: 로컬 개발 환경에서 외부 Callback 리다이렉트를 거치지 않고, 로컬 앱(또는 개발자 테스트 코드)이 공개 인증앱에 자격 증명(`phone_number`, `pin`)을 직접 호출하여 인증 세션 정보(`session_id`, `dev_token`, 사용자 권한 플래그 일체)를 즉시 발급받는 예외 API입니다.
* **접근 통제**:
  * 인증된 사용자의 `developer` flag가 **`"1"` (`developer`) 또는 `"2"` (`dev-leader`)인 경우에만 성공**합니다. 만약 일반 유저(`developer == "0"`)가 이 예외 API로 로그인을 시도하면 `403 Forbidden ("로컬 개발 예외 API는 developer(1) 이상 등급의 개발자 계정만 사용할 수 있습니다.")`을 반환하여 일반 사용자 계정의 무분별한 Direct API 호출을 원천 차단합니다.
* **Request (JSON 또는 Form)**:
  ```json
  {
    "phone_number": "01012345678",
    "pin": "1234",
    "client_origin": "http://localhost:5000"
  }
  ```
* **Response (`200 OK`)**:
  ```json
  {
    "valid": true,
    "dev_mode": true,
    "session_id": "e44d3204-1f1d-400a-b33c-3965fc71295c",
    "dev_token": "eyJ1aWQiOi...",
    "expires_in": 3600,
    "role_flag": "1",
    "developer_flag": "1",
    "developer_role": "developer",
    "is_manager": true,
    "is_super": false,
    "is_developer": true,
    "is_dev_leader": false,
    "roles": ["user", "manager", "admin", "developer"],
    "user": {
      "id": "e44d3204-1f1d-400a-b33c-3965fc71295c",
      "username": "01012345678",
      "name": "홍길동",
      "email": "gildong@thewayworks.net"
    }
  }
  ```

##### 2) `GET` & `POST /auth/api/dev/verify-session` (로컬 앱 -> 공개 인증앱 직접 호출 검증 예외 API)
* **용도**: 로컬에서 구동 중인 앱이 보유한 인증 세션 정보(`session_id`, `dev_token`, 또는 `Authorization: Bearer <session_id|dev_token>` 헤더)를 그대로 외부 공개 인증앱(`https://holyseeds.thewayworks.net/auth/api/dev/verify-session`)에 직접 Call하여 실시간 인증 Verification을 수행하는 엔드포인트입니다.
* **기존 `/auth/api/verify-session`과의 차이점 및 확장**:
  * 기존 `/auth/api/verify-session`도 `session_id` 쿼리 파라미터뿐만 아니라 `Authorization: Bearer <session_id>`, `X-Auth-Session: <session_id>`, `dev_token`을 모두 수용하도록 호환성을 확장합니다.
  * 전용 예외 엔드포인트인 `/auth/api/dev/verify-session`은 CORS(Cross-Origin Resource Sharing) 헤더(`Access-Control-Allow-Origin: http://localhost:*`)를 로컬 개발 Origin에 대해 명시적으로 허용하여, 로컬 프론트엔드(SPA)나 로컬 백엔드 어디서든 공개 인증앱으로 직접 호출할 수 있게 지원합니다.
  * 또한 `dev_token` (HMAC-SHA256 서명 및 만료시간이 포함된 토큰) 또는 `session_id`로 호출 시 호출 주체(또는 대상 세션)의 `developer` 등급 검증 및 로컬 개발 컨텍스트 로그를 남깁니다.
* **Request Parameters (Query / Header / JSON Body 모두 지원)**:
  * `session_id`: Keycloak 사용자 세션 UUID (Query `session_id`, Header `X-Auth-Session`, 또는 `Authorization: Bearer <id>`)
  * `dev_token`: (선택) `/auth/api/dev/direct-login` 또는 로컬 콜백 리다이렉트 시 발급된 서명된 개발 세션 토큰
  * `require_role`: (선택) 검증할 요구 권한 (`manager`, `super`, `developer`, `dev-leader`, 또는 개별 서비스 role flag)
* **Response (`200 OK`)**:
  ```json
  {
    "valid": true,
    "verification_mode": "direct_dev_call",
    "role_flag": "1",
    "developer_flag": "2",
    "developer_role": "dev-leader",
    "is_manager": true,
    "is_super": false,
    "is_developer": true,
    "is_dev_leader": true,
    "roles": ["user", "manager", "admin", "developer", "dev-leader"],
    "has_required_role": true,
    "user": {
      "id": "e44d3204-1f1d-400a-b33c-3965fc71295c",
      "username": "01012345678",
      "name": "홍길동",
      "email": "gildong@thewayworks.net"
    }
  }
  ```

##### 3) `/auth/login`의 로컬 개발 리다이렉트 브릿지 (`dev_mode=1` 또는 `localhost` redirect 감지 시)
* 로컬 앱이 브라우저를 `https://holyseeds.thewayworks.net/auth/login?redirect=http://localhost:5000/callback&dev_mode=1`로 보낸 경우:
  1. 사용자가 공개 인증앱 로그인 화면에서 로그인합니다.
  2. 공개 인증앱은 `redirect` URL이 로컬 개발 주소(`http://localhost(:포트)/...` 또는 `http://127.0.0.1(:포트)/...`)인지 확인합니다.
  3. **보안 검문**: `redirect`가 로컬 주소인 경우, 로그인한 사용자의 **`developer` 등급이 `1`(`developer`) 또는 `2`(`dev-leader`)인지 검증**합니다. 만약 일반 사용자(`developer == "0"`)라면 로컬호스트로의 세션 토큰 전달 리다이렉트를 거부하고 에러 메시지를 표시합니다.
  4. 개발자 등급이 확인되면, 브라우저가 로컬 서버로 이동할 때 쿼리 파라미터에 `session_id`와 서명된 `dev_token`을 첨부하여 `303 Redirect`합니다:
     `http://localhost:5000/callback?session_id=<user_id>&dev_token=<signed_token>`
     *(참고: 브라우저 자체가 개발자의 로컬 PC에서 실행 중이므로, 브라우저가 `http://localhost:5000/...`으로 이동하는 것은 외부 네트워크 방화벽/NAT와 무관하게 100% 작동합니다!)*
  5. 로컬 앱(`http://localhost:5000/callback`)은 쿼리로 받은 `session_id` / `dev_token`을 자신의 `localhost` 쿠키에 저장한 뒤, 백엔드에서 공개 인증앱(`https://holyseeds.thewayworks.net/auth/api/dev/verify-session`)으로 직접 Outbound HTTP Call을 보내 세션을 검증합니다.

### 파트 C. 로컬 개발 예외 API를 위한 보안 통제 가이드 (Security Control Proposal)

외부에 공개된 인증앱에서 직접 세션 정보를 받아 검증을 허용하는 예외 API는 편리하지만, 통제 장치가 없으면 세션 하이재킹(Session Hijacking), 무차별 대입(Brute-force), 피싱 리다이렉트(Open Redirect)에 악용될 위험이 있습니다. 이를 안전하게 통제하기 위해 **5단계 다층 보안 가드레일**을 함께 구현하고 `auth_spec.md`에 가이드로 명문화합니다:

1. **통제 1: 개발자 등급(`developer >= 1`) 기반 엄격한 자격 제한 (Role-Gated Exception)**
   * 로컬 개발 예외 API(`/auth/api/dev/direct-login`, `/auth/api/dev/verify-session`의 dev 모드, 그리고 `localhost`로의 세션 쿼리 리다이렉트)는 **Keycloak `developer` 속성이 `"1"`(`developer`) 또는 `"2"`(`dev-leader`)로 지정된 계정만** 사용할 수 있도록 강제합니다.
   * 일반 사용자(`developer = "0"`)나 권한이 없는 계정은 예외 API를 호출하거나 `localhost`로 세션을 리다이렉트받을 수 없습니다.

2. **통제 2: Redirect URI 화이트리스트 및 Localhost Loopback 검증 (Open Redirect 방지)**
   * 쿼리 스트링으로 세션 정보를 실어 보내는 예외 리다이렉트는 오직 `http://localhost(:[0-9]+)?(/.*)?` 및 `http://127.0.0.1(:[0-9]+)?(/.*)?` 패턴(또는 `.env`의 `ALLOWED_REDIRECT_HOSTS`에 명시된 도메인)으로만 허용합니다.
   * 공격자가 `redirect=https://attacker.com/callback&dev_mode=1`을 주입하더라도, 화이트리스트 검증에서 즉시 차단되어 외부 사이트로 `session_id`나 `dev_token`이 유출되지 않습니다.

3. **통제 3: HMAC-SHA256 서명 및 단기 만료 시간(TTL)이 적용된 `dev_token` 제공**
   * 단순 UUID(`session_id`)가 URL이나 로컬 로그에 노출될 위험을 완화하기 위해, 서버 비밀키(`DEV_AUTH_SECRET` 또는 토큰 해시 기반 키)로 서명되고 유효기간(기본 1시간, `3600초`)이 내장된 `dev_token` (`<user_id>.<timestamp>.<hmac_signature>`)을 발급 및 검증합니다.
   * 토큰이 만료되면 재발급을 요구하여 탈취된 옛 세션 값의 재사용을 방지합니다.

4. **통제 4: 환경 변수 기반 마스터 스위치 및 개발자 API 키 (`ALLOW_LOCAL_DEV_AUTH`, `DEV_API_KEY`)**
   * `.env` 환경 변수로 로컬 개발 예외 기능의 활성화 여부(`ALLOW_LOCAL_DEV_AUTH=true/false`, 기본값 `true`)를 중앙에서 즉시 On/Off 할 수 있도록 구현합니다.
   * 추가 보안을 원할 경우 `.env`에 `LOCAL_DEV_API_KEY`를 설정하면, 로컬 앱이 공개 인증앱에 직접 Call을 보낼 때 `X-Dev-Api-Key` 헤더를 함께 전송해야만 동작하도록 이중 잠금(Dual-Lock) 기능을 지원합니다.

5. **통제 5: 감사 로깅 (Audit Logging)**
   * 로컬 개발 예외 API가 호출될 때마다 서버 콘솔/로그에 `[DEV-AUTH AUDIT] user=<phone>, dev_role=<1|2>, client_ip=<ip>, endpoint=<path>` 형태로 명확한 감사 로그를 남겨 비정상적인 호출을 추적할 수 있도록 합니다.

## 4. 검증 및 테스트 계획 (리뷰 승인 후 실행)

1. `python configure_keycloak_schema.py` 실행을 통해 Keycloak `holyseeds` Realm에 `developer` 속성이 정상 등록되는지 확인.
2. 단위/통합 검증 스크립트를 통해:
   * `developer` 등급(`0`, `1`, `2`) 설정 및 `verify-session` 응답(`is_developer`, `is_dev_leader`, `developer_role`) 검증.
   * `require_role=developer`, `require_role=dev-leader` 권한 판정 검증.
   * 로컬 개발 예외 API(`/auth/api/dev/direct-login`, `/auth/api/dev/verify-session`) 호출 시 `developer >= 1` 계정은 통과하고 `developer == 0` 일반 계정은 `403 Forbidden`으로 통제되는지 검증.
   * `redirect=http://localhost:5000/callback&dev_mode=1` 리다이렉트 시 외부 도메인(`https://evil.com`)이 차단되는지 보안 검증.
3. 모든 검증 결과 및 생성된 산출물을 `notes/result_YYYYMMDDHHmm.md`와 `notes/history.md`에 최종 기록.
